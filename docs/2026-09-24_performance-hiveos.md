# 2026-09-24 性能与 HiveOS 对齐

在上一轮稳定性修复的基础上，这一轮处理两件事：一是降低每台矿机、每 10 秒的采集成本；二是补齐 HiveOS 日常运维最常用的消息流、看门狗、快捷操作和矿工日志。数据库新增迁移 `0003_snapshot_events.sql`，运行层版本升到 `0.1.8`。

## 性能

| 范围 | 之前 | 现在 |
|---|---|---|
| 采集方式 | 每 10 秒两次 `sudo rig-miner collect`：每次启动一个 Python 解释器，非 root 用户每次都写一条 auth.log | watchdog 每 10 秒把 system、mining 和最近消息写入 `/run/rigdeck/snapshot.json`；主控只执行一次 `cat /proc/uptime /run/rigdeck/snapshot.json`：不经过 sudo，也不启动 Python |
| 快照的时间 | — | 用矿机开机以来的单调时间换算样本时间，不依赖矿机时钟；超过 45 秒没有刷新就视为 watchdog 失效，自动退回旧的采集方式 |
| 快照权限 | — | 文件归 SSH 用户所有，权限 0400（root 连接时为 0600）。部署运行层时执行 `rig-miner set-reader <用户>` |
| 矿工统计 | watchdog 每个实例每 10 秒启动一个子进程读取统计 | XMRig、SRBMiner、cpuminer 在 watchdog 进程内直接读取；只有 HiveOS 自定义包仍需进入独立命名空间 |
| system 数据量 | 包含 snap 的 loop 设备、Docker 文件级 bind mount、veth 等虚拟网卡；`nvidia-smi` 每 10 秒运行一次 | 磁盘按设备去重，排除 loop 设备和文件挂载；排除虚拟网卡；`nvidia-smi` 结果缓存 60 秒；新增主网卡 IPv4 |
| 矿机磁盘写入 | `stats.json` 和 `cpu-sample.json` 每 10 秒写一次并 fsync | 改为原子替换且不 fsync（这类缓存丢了可以重建） |
| 数据库写入 | 每条观测单独一个事务 | 所有机器共用一个写入任务，每秒或每满 512 条，用一条 `UNNEST` 批量写入；同一批里同一台机器的同一类数据只保留最新一条去更新“最新值” |
| `latest_observations` | 默认 fillfactor | fillfactor 设为 70，autovacuum 的触发阈值降到 2% |
| 监控循环 | 每 10 秒查一次机器表并解密一次凭据 | 每 60 秒刷新一次，出错时立即刷新 |
| 任务列表 | 读出每台机器最多 1 MiB 的输出和编译后的部署快照，再在内存里清空 | 查询里直接不选这两列；详情页在任务结束后停止轮询 |
| 安装包上传 | 总超时 300 秒 | 只在 60 秒内没有任何数据块被接受时才判定失败；远端确认等待 120 秒 |
| 前端 | `latest()` 线性查找，1000 台时约 1600 万次比较；汇总栏和列表各算一遍 | 每个响应只建一次索引；汇总栏和列表共用同一份行模型 |

没有做“只拉增量”的遥测接口。矿机每 10 秒上报一次，页面每 10 秒轮询一次，两次轮询之间几乎每一行都会变，做增量省不了多少流量；精简汇总数据已经解决了主要的流量问题。

## HiveOS 功能对齐

- **消息流**：运行层把各类事件写入 `events.jsonl`（最大 1 MiB，自动截断）：矿工意外退出、看门狗重启（附原因和持续时间）、恢复次数用尽、整机重启、飞行表应用成功或回退、手动启停矿工、开机恢复、策略更新。这些事件随快照上报，入库时去重，保留 90 天。`GET /api/v1/machines/{id}/messages` 把矿机事件、任务结果和配置操作合并成一条时间线，最新的在前。单机页新增“消息”页签，概览页显示最近 8 条。MCP 新增 `machine_messages` 工具。
- **看门狗表单**：单机页“设置”里可以直接配置：启用开关、最低算力（带单位）、异常持续时间、重启间隔、窗口内最多重启次数、次数用尽后是否重启整机。保存后监控循环在约 1 分钟内通过 `rig-miner set-policy` 下发到矿机，不需要重新应用飞行表。矿机端的 `policy.json` 优先于飞行表快照里的策略。另外支持按算法设置最低算力（`min_hashrate_by_algorithm`）。
- **快捷操作**：单机页顶部提供重启矿工；“矿工”菜单可启动全部、停止全部或逐个实例控制；“系统”菜单可重启系统、关机（先脱离当前任务再执行，所以任务能先报告成功，不会停在“结果不明”）、执行命令、部署运行层；“BMC 电源”菜单可开机、优雅关机、强制重启、强制断电。每项操作都需要二次确认，提交后提示并附任务链接。
- **矿工日志**：`GET /api/v1/machines/{id}/instances/{instance}/log?lines=` 只读返回 `console.log` 末尾（最多 2000 行，去掉终端控制序列），不会接入 screen 会话。“日志”页签提供实例切换、行数选择和 5 秒自动刷新。MCP 新增 `miner_log` 工具。
- **性能页**：时间范围可选 1 小时、6 小时、24 小时、7 天、30 天；图表包括分算法算力、CPU 使用率、CPU 温度、内存，以及配置了 BMC 时的整机功耗。
- **矿机列表**：每行显示内网 IP、接受份额和拒绝率（拒绝率不低于 5% 时标黄）、矿工版本、CPU 使用率条和按阈值着色的 CPU 温度（75°C、85°C）；告警图标悬停时列出具体原因。去掉了 CPU 矿场里永远为空的“显卡”页签，以及没有实际功能的“Site map”，中英文混用的文字统一为中文。

## 升级

1. 先备份，然后更新主控：迁移 `0003` 会在启动时自动执行。
2. 在矿机列表全选后执行“部署 / 更新运行层”。在运行层更新到 0.1.8 之前，主控继续用旧方式采集，功能不受影响，只是没有消息流，也不能下发策略。
3. 验证方法：在单机页“消息”里能看到“运行层 0.1.8 看门狗已启动”；非 root 用户的 `/var/log/auth.log` 不再每 10 秒新增 sudo 记录。

## 本轮验证

- Rust 单元测试（`cargo test --workspace`）；PostgreSQL 集成测试 `postgres`、`flight_updates`、`resilience`，以及新增的 `telemetry_batch`（批量写入、硬件字段拆分、事件去重、消息合并、任务列表瘦身）和 `snapshot_monitor`（快照新鲜时不走 sudo 采集、忽略矿机时钟、策略只下发一次、事件只入库一次），各自在全新数据库上通过。环境是 PostgreSQL 16，与 CI 用的 18 不同。
- `cargo clippy -D warnings`：本轮新增代码没有告警。在 Rust 1.95 下，`application/src/jobs.rs` 里原有代码会触发两处 `collapsible_match`；CI 固定用 1.91.1，不受影响。
- Python：`test_runtime.py` 21 项（使用本地模拟的 screen）；新增的 `test_runtime_snapshot.py` 8 项；依赖安装、模块边界和 Redfish 夹具测试都通过。
- 前端：无法联网安装依赖，只在第三方模块替换为桩的情况下做了 TypeScript 语法和未使用变量检查。`schema.d.ts` 里的新接口是手工补写的，需要在本地执行 `npm run types && npm run build`，再运行 Playwright。
