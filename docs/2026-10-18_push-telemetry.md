# 2026-10-18 矿机主动上报统计

运行层版本升到 `0.4.0`，数据库新增迁移 `0010_metrics_skip_transport.sql`。

## 为什么改

之前主控每 10 秒对每台矿机开一个 SSH 通道执行 `cat /proc/uptime /run/rigdeck/snapshot.json`，每 60 秒再用 sudo 跑一次软件发现。连接池会复用 SSH 连接，并非每轮重新握手，但每轮仍需建立通道并传输完整快照和最近 40 条消息；1000 台约每秒 100 次统计请求，一台卡住的机器还会占着自己的采集任务等超时。

现在看门狗写完快照后交给独立发送线程推送。只保留一份待发送的最新快照，慢 HTTP 请求和硬件清单采集不会阻塞看门狗。主控提交指标数据库事务后才确认成功；写入失败不会更新增量基准、序号或新鲜度，同机请求串行提交，不同机器独立处理。事件另行确认，保存失败继续重发。

成功回复和 409 重同步回复均带 `X-Rig-Reply-Signature`：HMAC-SHA256 覆盖 `rigdeck-push-reply-v1\n{请求签名}\n{HTTP状态码}\n` 和原始回复字节。运行层验证后才采用策略、epoch 和确认序号，防止明文网络上的回复篡改或跨请求重放。更换推送地址或密钥会清空旧基准和退避状态。

## 现在怎么工作

| 项目 | 做法 |
|---|---|
| 方向 | 看门狗每 10 秒 `POST http://主控:8091/ingest/v1/push`；主控不再为统计主动连接矿机 |
| 压缩 | 请求体为 zlib（`Content-Encoding: deflate`）压缩的 JSON |
| 增量 | 主控确认收到一次完整快照后，后续只发与它相比变化的字段（对象按键、等长列表按下标），每 30 次（5 分钟）再发一次完整快照；主控重启或基准对不上时回 409，矿机立刻补发完整快照，不丢这一轮 |
| 消息 | 只发主控还没确认过的消息，主控在回复里返回已保存的最大序号；之前每轮都重发最近 40 条 |
| 软件、硬件 | 软件发现每 60 秒、硬件清单每小时随推送附带，不再需要主控用 sudo 去采 |
| 看门狗策略 | 矿机报告的策略摘要与主控不一致时，主控在回复里直接带上新策略，矿机本地应用；不再走 SSH `set-policy` |
| 认证 | 每台机器一个密钥：`HMAC(HMAC(主密钥, 标签), 机器 ID)`，由主密钥派生，不额外存库。请求头 `X-Rig-Signature` 是对压缩后请求体的 HMAC-SHA256；签名不对直接 401，不解压、不查库 |
| 防重放 | 请求体里带主控本次启动的随机 `epoch`，主控重启后旧报文一律不认；同一次运行内同一开机周期的 `seq` 必须递增，已被替换的开机 ID 不再接受 |
| 上限 | 压缩后最大 256 KiB，解压后最大 4 MiB（防解压炸弹） |
| 不缓存 | 推送失败不排队补发，下一轮的新快照会覆盖；被拒（401/404 等）时每分钟才重试一次 |

实测（同一台机器连续推送，真实主控和真实运行层代码）：8 卡、2 个实例的模拟快照，原始 JSON 约 4.4 KB，完整快照压缩后约 0.9 KB，之后每轮的增量约 **0.25–0.45 KB**。之前每轮 SSH 读取的是未压缩的完整快照加最近 40 条消息，按同样的模拟数据约 18 KB，另有 SSH 自身的握手和通道开销。

## 回退和兼容

- 主控仍保留原来的 SSH 读取，只是在 25 秒内收到过这台机器的推送时跳过。运行层低于 0.4.0、推送地址不通、防火墙挡住 8091、或者矿机离线时，主控照旧通过 SSH 读取并显示离线。
- 运行层 0.4.0 在快照里报告 `push_digest`。主控通过 SSH 读到它与期望值不一致（包括还没配置）时，自动用 SSH 下发推送地址和密钥（`rig-miner set-push`，密钥写在 0600 临时文件里，不出现在命令行），同一台机器 5 分钟最多一次。“部署运行层”完成时也会立即配置一次。
- 单机页“系统”里运行层版本下方显示“主动上报”或“SSH 读取”，可以直接看到每台机器走的是哪条路。

## 配置

`/etc/rigdeck/rigdeck.env`：

| 变量 | 默认 | 说明 |
|---|---|---|
| `RIGDECK_INGEST_BIND` | `0.0.0.0:8091` | 接收推送的监听地址；`off` 关闭推送，全部回到 SSH 读取 |
| `RIGDECK_INGEST_URL` | 空 | 矿机推送的完整地址，例如 `http://192.168.1.10:8091/ingest/v1/push`。留空时按每台矿机看到的 SSH 来源地址和上面的端口自动生成；主控经过 NAT 或有多个网段时请明确填写 |

接收端口是明文 HTTP：内容是矿机统计（算力、温度、矿池地址等），不含凭据，每个请求都带签名，防篡改和冒充，但不加密。主控面板本身的 `/ingest/v1/push` 路径同样可用，若矿机要经过 HTTPS 反向代理推送，把 `RIGDECK_INGEST_URL` 指向那个 https 地址即可（矿机需信任其证书）。

## 升级

1. 更新主控（迁移 0010 启动时自动执行），确认日志里有 `telemetry ingest listening`。有防火墙时对矿机网段放行 TCP 8091。
2. 在矿机列表全选后“部署 / 更新运行层”到 0.4.0。部署结果里 `push: configured` 表示已配置；或者等主控下一次 SSH 读取时自动配置。
3. 检查：单机页显示“主动上报”；消息里有“已启用主动上报：http://…”。

## 验证

- `python3 tests/test_push.py`（7 项）：压缩和签名、409 后立即补发完整快照、增量能还原出完全相同的快照、关键帧、主控重启、基准丢失、消息只发一次、回复里的策略在本地生效、密钥错误后退避、主控不可达不影响看门狗、`set-push` 校验与临时文件删除。增量格式的测试用例写进 `tests/fixtures/snapshot-patches.json`，Rust 端 `push::tests` 用同一份文件还原，两边格式不会悄悄分叉。
- Rust 单元测试：增量还原、签名校验、解压上限、密钥派生（按机器、按主密钥不同）。
- PostgreSQL 集成测试 `telemetry_push`：伪造签名和别的机器的密钥被拒、首次 409、完整快照入库并确认消息、回复里带策略、增量入库、重放被拒、未知基准要求重发、推送期间监控循环没有发起任何 SSH 读取、另一次主控运行不接受本次报文。原有 `snapshot_monitor`、`telemetry_batch`、`postgres`、`flight_updates`、`machine_batch` 同样通过。环境是 WSL 里的 PostgreSQL 14，与 CI 的 18 不同。
- 端到端：WSL 里启动真实 `rigdeck serve`，用真实运行层代码（真实采集）推送 4 轮：全部 200，`latest_observations` 的 system 为 `transport=push`，消息入库，矿机端 `policy.json` 收到主控的策略；未签名请求和错误密钥都是 401。
- 没有在真实矿机和真实网络上验证；Windows 下 `rig-infrastructure` 的测试程序被系统拒绝执行（权限，与本次修改无关），所以 Rust 测试都在 WSL 里跑。
